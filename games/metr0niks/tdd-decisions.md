# Metr0niks TDD decision history

Newest first. Status is Proposed until kr0 accepts or rejects it. The [TDD](tdd.md) holds the architecture; this file records the options and trade-offs behind it. These are technical-director proposals drawn from what the prototype already does and from the [GDD review](feedback/synthetic/gdd-review-2026-10-25/SYNTHESIS.md); none has been decided by kr0 yet.

| ID | Date | Decision | Options considered | Trade-off | Status |
| --- | --- | --- | --- | --- | --- |
| TDD-D17 | 2026-10-28 | A headless runner (`simulations/run.js`) with a scripted player plays whole excursions in Node, writes one metrics record per run to `tuning-runs/` and replays one run per batch to compare state hashes; `rules-check.js` asserts single rules in short scenarios | Sweep by hand in the mechanics lab; wait for the studio's `chronos-sim` (postponed) | Needed before any fun pass number can be swept (studio simulation standard); a game-local runner is throwaway once `chronos-sim` exists | Proposed |
| TDD-D16 | 2026-10-28 | Feel effects (hit-stop, stamps, camera punch, multi-kill text, cockpit voice) live only in the client and are driven by sim events; the sim never pauses or slows | Freeze the struck enemy in the sim for 60 ms | Keeps co-op in step and the rules renderer-free (GDD-D45, GDD-D46); the freeze has to be faked with an effect | Proposed |
| TDD-D15 | 2026-10-28 | Overtime, extract-now and call-ins arrive as new input bits (F, Enter or R, 1, 2) through `setInput`, and the post-wave-5 choice is a sim state with a 6 s timer | A separate command channel from the client | Input bits already reach the host every tick and replay with the input log; a command channel would need its own ordering and replay | Proposed |
| TDD-D14 | 2026-10-28 | The Warden is a group of linked entities in the enemy list (body, three platforms, three rider snipers, four legs) sharing a parent id, so targeting, damage, credit and snapshots reuse the existing enemy code | One big entity with hit zones | Linked entities reuse the sniper rules for the riders and the normal hit path; they need care when the parent dies (every child goes too) | Proposed |
| TDD-D13 | 2026-10-28 | Match stats are a sim-owned record per mech per wave, sent in a wave-clear event and in the run-over event, and written unchanged by the runner as its metrics record (GDD-D50) | Count stats in the client from events | One record serves the player's reports, contracts and the sweep; counting in the client would differ between host and guest and isn't available headless | Proposed |
| TDD-D12 | 2026-10-28 | Save v2: adds wear, upgrade levels, highest level extracted, lifetime records, a typed-seed flag, call-in slots and the in-match mark; drops carried armor; v1 codes migrate on load | Keep v1 and add optional fields | A version bump makes validation strict and the migration explicit; old codes still load | Proposed |
| TDD-D11 | 2026-10-28 | `create({tune})` merges an override object over a per-run copy of `T`; sector conditions and sweep variants both use it, and `MetroSim.T` is never mutated | Conditions as `if` checks in each rule; mutate `T` and restore it | One mechanism for conditions and sweeps, as the studio standard's overrides ask; inner functions must read the run's copy, which means one careful pass over `sim.js` | Proposed |
| TDD-D10 | 2026-10-28 | The climb plan (each level's condition, contract and bosses) is worked out from the climb seed by `Campaign.plan()` on its own seeded stream, never saved, and handed to the sim | Draw them inside each level's sim; save the plan | The garage can show the next level before a sim exists, no-repeat rules span the whole climb, and in-match randomness can't change it; a change to the plan code changes old seeds' climbs | Proposed |
| TDD-D9 | 2026-10-28 | One hit path: `hitEnemy` applies the GDD-D48 damage order and records kill credit; `hitMech` applies level and Elite scaling. Every weapon, blast, collapse, hazard and enemy attack uses them instead of calling `damage()` | Patch each of the 13 call sites | One place for the order, credit, stats and the Bulwark shield; it touches every weapon, so it comes first in the plan with rules-check coverage | Proposed |
| TDD-D8 | 2026-10-26 | The save carries an in-match mark written when a match starts; a save still marked on load counts as a death, so closing the game mid-match can't dodge the level reset (GDD-D28). The co-op revive runs inside the sim at wave clear (GDD-D24) | Save only at extract and death; detect leaving with a page-unload handler | Unload handlers don't run reliably when a tab is killed; the mark costs one extra write per match | Proposed |
| TDD-D7 | 2026-10-26 | Weapon upgrade levels (GDD-D23) are data on each owned weapon instance and in the save, read into a per-mech damage multiplier per weapon, next to wear (TDD-D5); values live in `T.upgrade` | Separate upgraded copies of each part in `PARTS` | One field per owned part keeps the parts table at 21 entries and lets sweeps change `T.upgrade` alone; the save and its validation grow by one field | Proposed |
| TDD-D6 | 2026-10-25 | Enemies and pods use flow fields over a walk grid rebuilt when voxels change, as the prototype does, instead of a navmesh | A navmesh with local rebakes | The grid is already built and updates with every collapse; a navmesh is more work and the TDD's old plan | Proposed |
| TDD-D5 | 2026-10-25 | Per-part wear is data on each owned part instance, applying GDD-D18 (wear 10% of armor lost ÷ max armor, helpful stat changes scaled by 1 − wear), replacing the prototype's single carried armor value | Keep the carried armor pool and charge repairs by fitted tier | Per-part durability matches GDD-D9 but needs per-part save data and a garage UI; the armor pool is built and simple | Proposed |
| TDD-D4 | 2026-10-25 | Disconnects are handled by the server holding the match and sending a full snapshot on rejoin | Drop the player and give the partner the mech; end the excursion | Holding state keeps the player's run but needs the server to snapshot the destroyed map; the prototype destroys a dropped mech | Moved to the backlog (GDD-D21) |
| TDD-D3 | 2026-10-25 | Single-player runs on the server too, so account progress, co-op and later PvP share one economy | Keep single-player in the browser with a local save and campaign code | Server-backed saves stop edited scrap; the browser version works offline and needs no backend | Moved to the backlog (GDD-D21) |
| TDD-D2 | 2026-10-25 | The rules stay a headless, deterministic simulation in `sim.js`, run by the room server and by Node for sweeps | A separate balance copy of the rules; the engine's own physics | One rules file keeps sweeps and the game identical; it ties the build to JavaScript until the engine choice is made | Proposed |
| TDD-D1 | 2026-10-25 | Co-op uses a server-run simulation with snapshots and client prediction of the player's own movement, as the prototype does | Lockstep between two clients; peer-hosted rooms | An authoritative server settles pod ties and damage in one place and fits later accounts (backlog, GDD-D21); it costs server hosting and the server code lives in a private repo | Proposed |
